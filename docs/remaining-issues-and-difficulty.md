# 現在の課題と対応難易度

**後続の実装あり：**「中」「中〜高」への対応と現在残る範囲は[対応記録](medium-difficulty-improvements.md)を参照。以下は対応前の棚卸しであり、CLI一括保存・結合前検査・TOYO表示差などを現在の未修正項目として扱わない。

2026-10-12。現行ソースの対応範囲、拒否条件、保存処理と、これまでの実機検証記録を照合した棚卸し。難易度は実装と正しさの検証を合わせた技術的な評価であり、日数の見積もりではない。今回の作業は棚卸しと文書整理で、変換処理は変更していない。

低＝局所的な修正と既存の検証で確認可能。中＝複数箇所の変更と専用の検証が必要。高＝描画・色・保存方式に踏み込み、実機との比較が必要。非常に高い＝出力構造や処理方式の大幅な拡張が必要。未判定＝問題の再現と原因の特定が先。

## 現在の基準

- 直近の自動テストは386件成功。有限の入力例での検証であり、全PDFや印刷結果の保証ではない。
- DICは基準の`dic1_fromai.ai`に合わせた旧版カラーブックのCMYK代替値。TOYOは独立したLabデータ・パレット。DICとTOYOのファイルは分離し、CMYK版パレットXMLは作らない。
- DIC1の実機比較では、特色・濃度・単純図形の編集属性と再保存後の外観を確認した。基準AIファイルは変更しない。
- `jimon_mars`の修正と再保存後に崩れないことはユーザー確認済み。他の構造まで確認済みという意味ではない。
- 全自動テスト、PDF表示の比較、Illustrator再保存の比較、印刷の分版確認は、それぞれ別の検証。

## 未対応機能と精度の制限

| 課題 | 現在の影響 | 難易度 | 対応に必要なこと |
| --- | --- | --- | --- |
| 文字を文字のまま編集可能にする | 対応文字もアウトラインになる。元がアウトラインなら文字情報がない | 非常に高い | Illustratorの文字データ・配置・フォント・字形キャッシュの整合性を再現。PDFだけでは元の文字列や組版意図を復元できない場合もある |
| 縦書き、Type3、一部のCID/CMap・フォント | ページ画像化、strictでは変換拒否 | 高 | フォント形式ごとの字形・配置対応と実例検証。対象を限定した追加対応は中〜高 |
| 元ICCプロファイル・インク成分の編集保持 | 対応ICC色は8ビットsRGBへ変換。元の印刷用色設定を編集データに完全保持しない | 非常に高い | 文書色空間、プロファイル、OutputIntent、画像・図形・透明処理を通した設計と印刷比較 |
| 一般のLab/Cal系・DeviceN・ICC付きグラデーション | DIC/TOYOの限定対応とは別。対応外は画像化または拒否 | 高〜非常に高い | Lab/Cal系の範囲拡張と、多インク・グラデーションの出力表現。DeviceNは特に難しい |
| 非線形の特色濃度、プロセス色のオーバープリントモード0 | 対応外は画像化。画像化で元の特色分版は失われる | 高 | 濃度関数とインクの合成を再現し、分版で検証。単純な特色濃度への置換だけでは足りない |
| 図形のソフトマスク、ページ全体の分離・ノックアウト | ページ画像化。Formの対応済み透明グループとは区別が必要 | 高 | マスク・グループ境界と合成順序を再現。同色空間の限定対応なら中〜高 |
| 文書と異なる色空間の透明グループ | ページ画像化 | 非常に高い | 色変換と透明合成、特色との相互作用を同時に検証 |
| メッシュ・タイルパターン・未対応の円形グラデーション | ページ画像化。円形の非等方変換、開始半径、外部焦点、Extend等に制限 | 高〜非常に高い | タイルや限定的な円形条件は中〜高。メッシュは新しい表現と補間の検証が必要 |
| インライン画像、画像ColorSpace別名、特殊な画像マスク | ページ画像化。異寸法・入れ子マスク、Indexed Matte、16ビット色キーマスク等が未対応 | 中〜高 | パーサー、資源の参照範囲、サンプリング・Decodeの対応。別名や16ビットマスクは過去の試行で描画差があり、単純な追加では済まない |
| ヘアライン、退化した線、特殊な破線・結合、グラデーションの線 | ページ画像化。対応する線も輪郭化される場合がある | 中〜高 | 条件ごとの形状生成と複数解像度での比較。ヘアラインは出力装置・解像度に依存 |
| 曲線の輪郭化・量子化の精度保証 | 近似差が残る。0.0025ptは分割基準で、最終輪郭の最大誤差保証ではない。画像は16→8ビット化 | 高 | 尖点・自己交差・極端な変換の誤差評価と処理量の制御。元の線としての編集性は別の課題 |
| 条件付きレイヤー・排他表示・動的表示 | ページ画像化。単純なOCGの表示・ロック・印刷属性は対応済み | 高 | 条件の評価とAIへの対応付け。AIに同等の動的機能がない条件は変換方針の選択も必要 |
| 一部未対応でもページ全体を画像化する方式 | そのページのパス、文字、レイヤー、特色分版が失われる | 非常に高い | 部分画像化へ変更するには描画順、クリップ、透明グループ、色空間をまたぐ依存を維持する必要がある |
| 注釈・フォーム等、暗号化PDF、前処理の併用制限 | 注釈ページは画像化。パスワード入力なし。`--combine`と`--outline-text`は併用不可 | 中〜高 | パスワード対応は中。注釈の外観を残す処理やレイヤーを壊さない前処理は中〜高。PDFの対話機能をAIで再構築することは現在の用途の範囲外 |
| 大容量・多数ページ・極端な座標 | キャンバス、1000アートボード、画像4000万画素、パスや展開数等の上限で拒否・画像化 | 中〜非常に高い | 実データで時間・メモリーを計測して改善するのは中。処理方式の変更やAI形式の制約回避は高以上。上限を外すだけでは解決しない |

主な実装根拠：`src/pdf2ai/vector.py`、`fonts.py`、`layers.py`、`color_management.py`、`native.py`、`multiboard.py`。これらは未対応条件を明示的に拒否し、通常モードでは可能な場合にページ画像化へ切り替える。

## 保存・検査・運用

| 課題 | 現在の影響 | 難易度 | 対応に必要なこと |
| --- | --- | --- | --- |
| CLIの複数出力を全件成功時だけ公開する方式 | 後の変換が失敗しても先に成功したAIは残る。Scribusの一括公開とは異なる | 中 | ステージングと一括公開をCLIに組み込む。既存の逐次保存を変えるか、選択式にするかの設計 |
| CLIのAIとJSONレポートの一括保存 | レポート保存が失敗した場合、AIが残って終了コードは失敗になることがある | 中 | AIとレポートを同じ公開処理にまとめ、通常エラー時の復元を検証 |
| 結合条件の事前検査 | 各ページが変換可能でも、結合の配置・色空間・特色定義の競合は変換時に判明 | 中 | 公開を伴わない結合計画を事前検査と共用。配置計算と検査の重複を避ける |
| 全未対応理由の列挙 | 現在は各ページの最初の未対応理由。直すと次の理由が出る場合がある | 高 | 一つの拒否後も安全に解析を続ける仕組み。最初の理由だけを改善する案とは工数が異なる |
| 強制終了・停電・並行書き込み時の一式保存 | 通常エラーの復元はあるが、複数ファイルを完全に同時確定する保証はない | 高 | 復旧記録と再開時の回復設計。複数ファイルの完全な原子性には公開単位の設計変更が必要 |
| 大きな処理のキャンセル・時間制限の範囲 | ScribusのPDF生成中、公開・復元中などには現在のキャンセルやタイムアウトが及ばない | 中〜高 | Scribus APIの制約と復元の安全性を確認。途中中断だけを追加すると出力保護を損なう |
| 現行一覧と過去記録の混在 | 古い未対応項目・検証件数を現在の状態と誤読しやすい | 低 | 現行の一覧を一本化し、過去の記録への入口に履歴と明記。今回、本書への案内を追加 |

主な実装根拠：`src/pdf2ai/cli.py`、`preflight.py`、`batch_publish.py`、`path_conflicts.py`、`integrations/scribus/export_ai.py`、`progress_dialog.py`。

| 対象 | 現状 | 難易度・必要な検証 |
| --- | --- | --- |
| DIC 448で文字が太く見えた実例 | 原因未確定。合成例や文字なしのファイルが正常でも解決済みにはできない | 未判定。元データ・条件で再現する調査が先。原因によって局所修正から文字描画の改修まで変わる |
| 最終実装での実機比較をまとめて再実行 | DIC1、TOYO等は個別に確認済みだが、すべての実機例を最後の変更後に一律再確認したわけではない | 中。現在のツールで生成→Illustrator再保存→再読込し、外観・特色・編集属性を比較 |

## 優先順位

1. Illustratorを使える間に、現行ツールの実機比較をまとめて再実行し、基準結果を保存する。DIC 448の実例があるなら再現調査もここで行う。
2. 印刷用途に必要な特色分版・オーバープリント・色管理を検証する。画面上の一致だけでは、この用途の確認を代替できない。
3. CLIの一括保存、AIとレポートの一括公開、結合前の検査を改善する。描画方式の大改修より範囲を限定しやすい。
4. 実際の制作データで遭遇する透明・画像・グラデーション条件から対応を広げる。全未対応を一度に解消するより、対象条件を決める必要がある。
5. 文字編集・完全な印刷色保持・部分画像化は大きな開発項目として扱う。

## 残課題から除外した修正済み項目

文字がなく問題箇所もないファイルでの不要なチェック画面、レポートの無断上書き、DIC1の特色・標準出力属性の基準差、DIC正規化時の深いForm参照、出力名の大小文字・Unicode・ハードリンク等の競合は修正済み。RGB文書内のCMYK画像の過去の描画差も対応が入っており、古い数値をそのまま現行の未修正不具合とは扱わない。これらの修正は、上記の汎用的な色管理・全入力保証とは区別する。
